# Pawket on Android

Pawket's Android app is the official Solana Mobile **webshell** around the
hosted web app, plus the few things a phone does better. The web app stays
the product — its pages, game rules, sends and server routes are the ones
in this repository — and the shell adds the wallet apps on the phone, the
share sheet, the gallery, the calendar, haptics, the back gesture, launcher
shortcuts and links that open in the app. Nothing about a pet, a key or a
transaction lives in Kotlin.

The release record and its evidence: `docs/ANDROID-HANDOFF.md`.

## Where it lives

| Path | What it is |
| --- | --- |
| `android/` | The Gradle project. Generated by `npx solana-mobile@0.5.0 webshell init` (commit `d16ffd1`), then made Pawket's in the commits after it |
| `android/app/src/main/java/app/pawket/android/MainActivity.kt` | The one WebView: lifecycle, back, splash and offline screens, renderer recovery, shortcuts, links handed to the app |
| `…/WebShellViewClient.kt` | What may load inside (Pawket's origin only) and the wallet's intents |
| `…/WebShellChromeClient.kt` | New windows (Pawket's stay, others go to the browser); every permission denied |
| `…/PawketBridge.kt` | The six requests the page may make of the phone |
| `android/app/src/test/…/BoundaryTest.kt` | JVM tests for the origin, picture and file-name checks |
| `src/lib/native/android.ts` | The page's half of the bridge, and `useHere()` ("this app" / "this browser") |
| `src/lib/solana/browser-client.ts` | `registerPhoneWallets()`: Mobile Wallet Adapter, Android only |
| `public/.well-known/assetlinks.json` | The site's statement that its links may open in `app.pawket.android` |
| `scripts/android-release.sh` | The signed release build, and what it prints to record |

## How it works

**The page.** The APK loads `SOLANA_MOBILE_URL` from `android/gradle.properties`
(`https://pawket.world/home`). Only that origin — scheme, host and
port — loads inside; another site opens in the browser; `solana-wallet:`
starts the wallet app; `intent:` links are made safe; `file:`, `content:`,
`data:` and the rest go nowhere. A release build refuses a start URL that is
not https. Cleartext is allowed only to `localhost`/`127.0.0.1`, which
Mobile Wallet Adapter itself needs (`ws://localhost:<port>` to the wallet).

**The wallet.** `@solana-mobile/wallet-standard-mobile` 0.6.0 registers
"Mobile Wallet Adapter" as one more Wallet Standard wallet, on Android only
and loaded only there. Inside the shell its user agent carries
`Solana Mobile Web Shell`, which the adapter (≥ 0.5.1) reads to use local
association in a WebView and to skip Chrome's Local Network Access prompt;
the shell launches the wallet's intent and tells the page it blurred. The
connect sheet calls it "A wallet app on this phone" — Seed Vault, Phantom,
Solflare, whichever the player has. Signing is `sign_transactions`: the
wallet returns the whole transaction, so `send.ts` is unchanged — the
sponsor still signs first as fee payer, the wallet signs as owner, the
message is checked to be the one built, and it is sent with preflight on.
A wallet that declines, closes or cannot be found reads as one sentence
that says nothing was sent (`mobileWalletProblem` in `transactions.ts`).
If a broadcast reply or confirmation lookup is lost, the shared send path
looks up the existing signature. It never resends or builds a replacement;
an unresolved outcome keeps its Explorer receipt and says to check before
trying again. Only a confirmed record triggers the care moment and haptic.

**The bridge.** `WebViewCompat.addWebMessageListener` injects
`window.PawketAndroid` into Pawket's origin only; requests from any other
frame or origin are dropped. Each is JSON `{ id, op, … }`, checked field by
field, answered `{ id, ok, reason? }`:

| `op` | The phone | Asks for a permission? |
| --- | --- | --- |
| `share-image` | the print, as a PNG checked by its signature, to `cache/shared/` and the system share sheet through a read-only `FileProvider` URI; yesterday's files are cleared | no |
| `save-image` | the print into `Pictures/Pawket` through MediaStore | no (minSdk 29) |
| `share-link` | a link to a page of Pawket's (any other is refused) to the share sheet | no |
| `remind` | the calendar app, opened on a daily event (30 days) with the words of the web's `.ics`; the player saves it there | no |
| `haptic` | `done`, `cheer` or `refuse` as the view's own haptic feedback, so the phone's touch-feedback setting decides | no |
| `room` | the room's ground colour and day or night for the status and navigation bars | no |

It never carries a key, a transaction, a file path or a URL to load. The
app's only Android capability permission is `INTERNET`. AndroidX also adds
an app-private signature permission for its internal receiver, with no runtime
prompt or access to player data.
Failed photo storage leaves no published partial image and reports failure.
Each shared photo has its own temporary file, so a later photo cannot replace
one another app is reading. Native feedback failure cannot undo a saved care.
External `intent:` links accept only navigation schemes and are rebuilt without
the page's components, selectors, extras or permission flags.

**The phone.**
- Back closes the page's newest open sheet or dialog (`useBackCloses`),
  then goes back a page, then sends Pawket to the background with
  everything as it was.
- Every configuration change — rotation, dark mode, font size, a keyboard —
  is handled in place, so a send waiting on the wallet is never reloaded.
  The WebView is paused when hidden, never timer-stopped, so a wallet app
  answering while Pawket is behind it is heard. After the system kills the
  process, the page and its history come back; if the renderer dies, a new
  WebView opens where the old one was.
- No pull-to-refresh: a drag in the room or a game never reloads a send.
- Edge to edge, padded to the system bars and the keyboard; the bars wear
  the room. Text follows the phone's font size. The theme is DayNight, so
  a player with no room picked gets Daylight or Lamplight as the phone is set.
- Long-press the icon: Home, Playground, Park. Links to a Passport, a guild
  or a place open in the app once Android has verified
  `/.well-known/assetlinks.json` for the release key.
- Haptics: a care kept (after the save, or after Solana confirms), a new
  level, a refusal. Never while signing. Profile has a switch.

## Storage, and what moves between phones

| What | Where it is kept | What ends it |
| --- | --- | --- |
| Pets in this app, the player's name, look, outfits, room, settings | this app's WebView storage on this phone — not Chrome's, not a wallet browser's | uninstalling, or clearing the app's storage. The app is not backed up (`allowBackup="false"`), and a phone-to-phone transfer leaves WebView data out (`data_extraction_rules.xml`), so a new phone starts empty |
| Pets on Solana, their Passports, guilds, the closet | Solana | nothing on the phone: connect the same wallet anywhere |
| The Mobile Wallet Adapter authorization | this app's storage (the adapter's cache) | disconnecting, or clearing the app's storage |
| A Pawket Wallet device key | this app's IndexedDB: a non-extractable WebCrypto Ed25519 key that cannot be read, exported or backed up | uninstalling, or clearing the app's storage. Unlink it from the wallet (any device) and link this app again |

A pet in Chrome does not appear in the app, and the other way round; the
words on screen say "this app" inside it (`useHere()`). Keeping a pet on
Solana is the way to have it everywhere. The release origin must stay the
same: a new origin is new, empty storage.

The device key is the phone's WebView's, not Seed Vault's. Making it needs
WebCrypto Ed25519, which the emulator's System WebView 134 does not have:
there the app says to update Android System WebView. Every action on Solana
goes through a linked Pawket Wallet, so until it is updated nothing on
Solana is sent from that phone; play in the app is unaffected.

## Build

Prerequisites: JDK 17 or later (21 is what is used), the Android SDK with
`platforms;android-37.0` and `build-tools;37.0.0`, and Node with pnpm for
the web app (`corepack pnpm` selects the version pinned in `package.json`).
Dependency overrides and the MWA optional-peer workaround live in
`pnpm-workspace.yaml`, which the pinned package manager reads. Pinned in
the project: Gradle 9.7.1 (wrapper, checksum
verified), Android Gradle Plugin 9.3.2, Kotlin 2.4.10, Compose BOM
2026.08.00, `androidx.webkit` 1.17.1, `androidx.core` 1.19.0,
`core-splashscreen` 1.2.0; minSdk 29, target and compile SDK 37.

```sh
export JAVA_HOME=…            # a JDK 17+
export ANDROID_HOME=…         # the SDK
echo "sdk.dir=$ANDROID_HOME" > android/local.properties

# A debug build of this checkout's web app, on a phone or emulator over adb:
pnpm build && pnpm start -p 3000
adb reverse tcp:3000 tcp:3000
(cd android && ./gradlew assembleDebug -PSOLANA_MOBILE_URL=http://localhost:3000/home)
adb install -r android/app/build/outputs/apk/debug/app-debug.apk

# JVM tests of the shell's checks:
(cd android && ./gradlew testDebugUnitTest)

# Lint with the configured release domain (localhost is not an App Links domain):
(cd android && ./gradlew lintDebug lintRelease)

# The signed release, against https://pawket.world/home:
PAWKET_ANDROID_KEYSTORE=/path/to/pawket-release.jks scripts/android-release.sh
```

A debug build is `app.pawket.android.debug`, named "Pawket dev", installs
beside the release with its own storage, and lets Chrome DevTools attach
(`adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>`). A
release build sets WebView debugging off and never writes the page's
console to the log. The `userdebug` emulator still exposes DevTools: Chromium
always enables it on development OS builds. Confirm it is absent on a
consumer phone; do not mistake that emulator override for APK configuration.

To test signing without a wallet of your own, install the official Mobile
Wallet Adapter test wallet (`npx solana-mobile device install fakewallet`, or
the same APK from the MWA repository's releases); the sponsor pays, so its
empty devnet account can adopt and care.

## Release and hosting

The APK holds the shell, not the web app: a deploy of `main` changes what
the app shows. So:

- A web change that the shell already supports ships by deploying, and is
  checked in the release APK afterwards.
- A change to `android/` needs a new APK: `SOLANA_MOBILE_VERSION_CODE` up
  by one in `android/gradle.properties`, signed with the same key.
- Each release records the shell commit, the web commit that production
  serves, the APK's SHA-256, its version and the cluster (devnet). The
  current record is in `docs/ANDROID-HANDOFF.md`.

**The release key** (`pawket-release.jks`, PKCS12, alias `pawket`, RSA
4096, certificate SHA-256
`A2:EF:F8:EE:78:3B:3E:F2:00:96:D5:EC:C6:1D:EF:F8:5A:13:37:56:8F:59:68:4A:03:67:DE:F0:72:B2:61:21`)
is the app's identity for good: every update must be signed with it, and
`assetlinks.json` names it. It is kept outside the repository (with
Pawket's other keys, in the main checkout's ignored `.keys/android/`) and
its password in the login Keychain of the Mac that made it. Back both up
somewhere only the owner holds; never commit, upload or paste either. The
dApp Store requires a key used for it alone — if Pawket ever ships on Google
Play, that is a different key, and its fingerprint joins `assetlinks.json`.

## Known limits

- Release 0.1.1 (2) opens `pawket.world`; 0.1.0 used
  `pawket-pets.vercel.app`. Install the update with the same package and
  signer, without clearing data. Guest pets, player settings and device keys
  remain scoped to their original web origin, so the new origin starts with
  separate local storage. Keep a guest pet on Solana in the old app before
  updating if you want to bring it along. Reconnect the same wallet on the
  new domain to read its pets, and link the device again with owner approval.
  No device key is exported. The old host and APK remain available; the app
  never restores the old origin's saved page into the new release.
- Mobile Wallet Adapter 0.6.0 (protocol 2.3.0) is patched locally
  (`patches/`). Every session closes when it ends — signed, refused, timed
  out or failed — where 0.6.0 left a failed one open forever, the wallet's
  screen waiting for a request that never came. A wallet that no longer
  honours the token it issued (restarted, cleared, expired) is asked to
  authorize again in the same session, so the first try signs; a different
  account is refused. A session the wallet closes rejects the request
  waiting on it at once (protocol 3.0.0's fix, backported). Connecting
  authorizes before it asks for capabilities. A wallet app gets a minute to
  open and unlock, and 85 seconds to answer; Pawket's own signing deadline
  is longer, so a retry never opens a second session over a first.
  `mobile-session.test.ts` holds the session rules; consumer-wallet
  behaviour remains part of the physical-phone check.
- Pawket needs a connection to open. A page already open keeps working for
  a pet in this app; anything on Solana says it could not reach it and sent
  nothing. There is no offline cache of the site.
- No push notifications (deferred, `docs/PRODUCT.md`); a reminder is an
  event in the player's own calendar.
- Seed Vault is reached through its wallet app by Mobile Wallet Adapter;
  Pawket uses no Seed Vault SDK and holds no key of the player's.
